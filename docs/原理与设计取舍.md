# 原理与设计取舍

简体中文 | [English](design-notes.md)

> 这篇是写给「想搞懂这个相机的 GPU 到底在忙什么」的人，包括三个月后忘光了的我自己。
> 使用方法、构建命令请看 [README](../README.md)，这里只聊为什么。

## 先说结论：一帧画面的一生

我给自己定的规矩是：**每一个 pass 都要能对应到一台真实胶片相机里的某个东西**。不然滤镜写着写着就成了玄学调参，改一个数字全图变色，谁也说不清为什么。

```
真实世界                     CineGL 里
────────                     ─────────
镜头    畸变、色散、暗角   →  input pass（input_body.glsl）
胶片曝光 高光散射成光晕    →  glow pass（Dual Kawase 金字塔）
冲洗    显影出颜色         →  film pass 里的 3D LUT
银盐    颗粒               →  film pass 里的噪声
放映    看片子             →  present pass（还顺手画了斑马纹、峰值、波形图）
```

按这个顺序排，好处是「物理上先发生的事情先算」：光晕是光在胶片里乱跑，它应该发生在调色之前；你不会见过「先冲洗、再让照片自己发光」的胶片。

## 为什么核心用 C++ 写

一开始我是想全用 Kotlin 的，`GLES30.glXxx` 一路调过去，省心。后来想明白一件事：**GL 代码最难调的不是 GL 调用，而是 GL 调用前面的那堆数学**——坐标怎么转、LUT 怎么烘、模糊金字塔每层多大。这些东西在手机上调，就是「改一行 → 编译 → 装机 → 对着屏幕眯眼睛」，一轮三分钟。

所以我把它们全拎出来放进 C++ 的 `core/`，分成两半：

- `cinegl_cpu`：纯数学，不碰 GL，`core/scripts/run_host_tests.sh` 在电脑上两秒跑完两百多个断言；
- `cinegl_gles`：真正调 GL 的那部分，尽量薄，「画多大、参数多少」都去问 `PassPlan` 要。

JNI 那层（`cinegl_jni.cpp`）只做类型转换，一行业务逻辑都不放。这样出了问题，先在电脑上跑单测，绿了再上手机——大部分 bug 根本活不到上手机那一步。

> 唯一一个活到了手机上的 bug：`film.frag` 里我把光晕的纹理和光晕的强度都叫 `uHalation`。GLSL 编译器当场翻脸，C++ 单测却一脸无辜——它压根不编译 GLSL。于是补了 `validate_shaders.sh`，用 NDK 自带的 `glslc` 在电脑上把每个 shader 编一遍。教训：**测不到的地方，迟早有人替你测，通常是最近的那台手机**。

## 第一站：相机纹理和那个神秘矩阵

Camera2 把画面送进 `SurfaceTexture`，GL 这边拿到的是一张 `GL_TEXTURE_EXTERNAL_OES` 外部纹理。它有两个脾气：

1. **只能用 `samplerExternalOES` 采样**。因为它背后可能是 YUV 格式的 GraphicBuffer，YUV → RGB 的转换由驱动在采样时偷偷做掉。好处是省事，坏处是你没法拿它当普通纹理用（比如绑到 FBO 上），所以第一个 pass 必须先把它「抄」到一张普通 RGBA 纹理里，后面的 pass 才好干活。
2. **必须乘 `getTransformMatrix()`**。这个 4x4 矩阵里装着传感器安装角度带来的旋转、上下翻转、以及缓冲区边缘的裁剪。不乘它，你会得到一张躺着的、可能还是倒着的画面。

我在它后面又乘了一个画幅裁切矩阵：

```
texMatrix = stMatrix × cropMatrix
```

读法是从右往左：先把「画面坐标」映射到「直立图像里的裁切区域」，再由相机矩阵映射到缓冲区。16:9、2.39:1、1:1 全靠 `cropMatrix`，GPU 不用多画一个像素。

### 坐标系：踩坑重灾区

全项目我只允许存在一种画面：**竖持手机时看到的直立画面，长边竖直**（`FrameGeometry.h` 顶部那段注释是整个项目的宪法）。然后有三件事会把方向搞乱：

| 谁 | 它的习惯 | 我怎么处理 |
|---|---|---|
| GL 纹理坐标 | (0,0) 在左下 | 全管线统一按 GL 习惯 |
| 位图 / JPEG | 第 0 行在最上面 | 拍照输入矩阵里翻一次（`stillInputMatrix`） |
| `glReadPixels` | 从最底下一行开始读 | 读回前画的时候再翻一次（`outputMatrix` 的 `flipY`） |

所有旋转、镜像、翻转都写成「输出坐标 → 输入坐标」的仿射矩阵，用三个点 `f(0,0)`、`f(1,0)`、`f(0,1)` 就能确定。推导一次写进单测，以后谁再怀疑，跑一下就知道了——比在纸上画箭头靠谱，我画过，画到第三张开始怀疑人生。

### 录像为什么永远是横的

竖着拍视频，最直觉的做法是让编码器吃一个 1080x1920 的竖缓冲。但不少硬件编码器对「宽 < 高」并不友好，`isSizeSupported` 可能直接说不。

我的做法：**编码缓冲永远横着（宽 ≥ 高）**，竖拍时把画面顺时针转 90° 塞进去，再在 MP4 里写一个旋转元数据，让播放器转回来。手机系统相机也是这么干的。横拍时缓冲本身就是正的，元数据为 0，连不认元数据的老播放器都不会翻车。（`planVideoOutput`，单测里把四个朝向都过了一遍。）

拍照就不玩元数据了，直接把像素转正——EXIF 方向标签在各家相册里的支持程度，懂的都懂。

## 第二站：Log 是什么，为什么我做了两种

Log 的本质很朴素：**用对数曲线给信号重新分配码值**。人眼对暗部变化更敏感，线性编码却把一半的码值浪费在最亮的那一档上。Log 把暗部拉开、高光压扁，录出来是一张灰蒙蒙的片子，留给后期调色的余地更大。

我自己定了一条曲线叫 CineLog（`Color.cpp`），关键点是：

```
线性 0    → 0
线性 0.18 → 0.454   （18% 中灰，和业界的 Log 差不多落在 0.4 出头）
线性 1.0  → 0.752   （100% 白，上面还留了 1/4 的码值）
线性 4.0  → 1.0     （白以上 2 档的余量）
```

为什么要给 1.0 以上留余量？因为后面要加光晕。光晕是「加」上去的光，加完很容易超过 1.0；Rec.709 编码在 1.0 一刀切，高光直接糊成一片白，CineLog 则还能装下，交给 LUT 里的肩部曲线慢慢压回来。**所以开 Log 后光晕会好看很多**——这不是玄学，是码值够用。

然后是两种实现：

- **GPU 模拟**：相机照常输出 Rec.709，我在 input pass 里解码回线性、再编码成 CineLog。工作流和真 Log 一模一样（灰片、LUT 监看、录原片），但必须老实承认：**宽容度不会凭空变大**，ISP 已经截掉的高光，GPU 变不回来。它的价值是教学，以及给光晕留空间。
- **ISP 曲线**：Camera2 允许用 `TONEMAP_MODE_CONTRAST_CURVE` 替换 ISP 的色调曲线。我把 CineLog 采样成 64 个点塞进 `TONEMAP_CURVE`，ISP 直接出 Log。传感器线性信号在 ISP 内部是高精度的，在那里套曲线再量化成 8 bit，比 GPU 拿到 8 bit 之后再折腾要干净。可惜不是每台手机都支持，模拟器更是「收到了，但不干」——请求里曲线一个点不少，像素纹丝不动。

### LUT 烧录 vs 仅监看

真电影机的标准工作流是：**录 Log 原片，监视器上套 LUT 看效果**。我把这个做成了一个开关：

- 烧录开：屏幕、文件都是调好色的成片；
- 烧录关：屏幕上照样是成片，文件里却是灰片。

实现上一点都不难，因为每帧本来就有两张纹理：`signal`（镜头之后、调色之前）和 `graded`（成片）。录像时让编码器画哪一张，一个 `Plane` 枚举就决定了。这就是把管线拆成多个 pass 的好处——中间结果天然就在那儿，想要哪张拿哪张。

## 第三站：3D LUT，以及为什么要「烘焙」

影调的配方很复杂：曝光、白平衡、通道串扰、饱和度、色相微调、S 曲线、分离色调、跳漂、褪色……每个像素都算一遍？手机 GPU 会用风扇声（如果它有风扇的话）表达不满。

所以我在 CPU 上把配方「烘焙」成一张 33×33×33 的查找表：对色彩空间里的 35937 个格点各算一次，存进 3D 纹理。GPU 每个像素只做一次 `texture(lut, rgb)`，硬件三线性插值白送。配方再复杂，GPU 的开销都一样。

几个值得记住的细节：

1. **半个格子的偏移**。格点在纹理里是「格子中心」，`texture()` 的坐标 0 和 1 却是纹理的边缘。直接拿颜色当坐标采，两端会各偏半格。正确写法：

   ```glsl
   vec3 uvw = s * ((size - 1.0) / size) + 0.5 / size;
   ```

   不加这一行，影调整体会轻微发灰——这种 bug 最阴，因为它「看起来也还行」。

2. **Log 开关要重烘**。表的输入是「工作信号」，开 Log 后信号变成了 CineLog 编码，表里必须包含「先解码 Log」这一步。所以 `LutBank` 记着当前编码，一变就作废所有表、后台重烘；用一个 generation 计数丢掉过期结果，免得手快来回切时旧表半路杀回来。

3. **中性 LUT + 影调 LUT 两张表**。「影调强度 0–10」不是重烘一张淡一点的表，而是在 shader 里 `mix(中性, 影调, 强度)`。拖滑杆不用等 CPU，丝滑。

4. **导入的 `.cube` 默认吃 Rec.709**。网上绝大多数创意 LUT 都是 709 → 709 的，所以开 Log 时我先把 Log 信号转成 709 再喂给它，而且这一步也是烘焙进表里的，GPU 无感。

## 第四站：光晕和柔光——Dual Kawase

光晕（halation）是胶片的老毛病：强光穿过乳剂，被片基反射回来，再次曝光最底层的红色感光层，于是高光边缘一圈红橙。柔光（Pro-Mist 那种滤镜）则是让亮部的光往四周散，整体反差变软。

两者本质都是「把高光模糊一下再加回去」。模糊我选了 **Dual Kawase**：每一级尺寸减半，降采样 5 个采样点、升采样 8 个。级数越多半径越大，但每一级像素只有上一级的 1/4，总开销收敛得很快。在手机上，它是我见过「大半径模糊」性价比最高的方案。

我的几条坚持：

- **在线性空间加光**。光的叠加是物理上的加法，在 sRGB 编码值上加会让亮部发灰发脏。`glow_prefilter.frag` 先解码再提取高光，`film.frag` 先解码再叠加，叠完再编码回去。
- **level 0 短边固定约 540 像素**。预览是 1080p，照片可能是 4000 万像素，如果金字塔从各自的分辨率开始减半，同样的「光晕 5」在照片上会小得可怜。固定起点之后，模糊半径和分辨率无关，预览里看到什么，照片里就是什么。
- **模糊结果用半精度浮点**。线性光的高光会超过 1.0，RGBA8 存不下；`RGBA16F` 能当渲染目标的话就用它（需要 `EXT_color_buffer_half_float`），不能就退回 RGBA8，效果打点折扣但不崩。
- **升采样写回上一级**。那一级的降采样结果用完就没用了，原地复用省一套显存。

## 第五站：颗粒

颗粒最容易做成「电视雪花」。真正的银盐颗粒有三个特征，我挨个照顾：

1. **一团一团的**：不用逐像素白噪声，用值噪声（格点放随机数、格子里平滑插值），叠两个频率；
2. **中间调最明显**：纯黑处银盐全没了、纯白处全满了，都看不到颗粒，所以强度乘了一个在 0.5 处最大的抛物线；
3. **每帧都在动**：随机种子用帧序号。

随机数用的是 PCG 风格的整数哈希，而不是祖传的 `fract(sin(x) * 43758.5453)`。后者在不同 GPU 上精度不同，有的机器上会出现规律的条纹——别问我怎么知道的，问就是曾经在一台手机上看到过满屏的斜线。

颗粒尺寸同样按「画面短边 / 1080」缩放，理由和光晕一样。

## 镜头的小毛病：暗角和色散

- **暗角**用的是自然暗角的 cos⁴ 定律：`亮度 ∝ 1 / (1 + (r·k)²)²`。比随手写一个 `smoothstep` 更像真镜头——衰减在边缘才开始明显，中间大部分区域几乎不受影响。坐标先乘宽高比，保证暗角是圆的，不会被 2.39:1 的画幅拉成橄榄。
- **色散**：R、B 两个通道沿径向往相反方向错开一点点，越靠边越明显。只在 input pass 里多采两次样，便宜。

两者都在线性空间做，因为它们本质是「光量变了」。

---

## 监看：只给眼睛看的东西

峰值对焦、斑马纹、波形图都只在 present pass 里画，**永远不会进入录像和照片**——这也是为什么上屏要单独一个 pass，而不是让 film pass 直接画到屏幕上。

我最喜欢的是波形图，它的做法有点反直觉：**用顶点着色器做散点图**。

```
glDrawArrays(GL_POINTS, 0, w * h);   // 不传任何顶点数据
```

每个点用 `gl_VertexID` 算出自己对应缩小画面里的哪个像素，横坐标 = 像素所在的列，纵坐标 = 它的亮度。开加法混合，同一个位置落的点越多就越亮——一个示波器就画出来了，CPU 一个像素都没碰。这是 ES 3.0 的 `gl_VertexID` 和 `texelFetch` 带来的福利，ES 2.0 时代做不到这么干脆。

## 一帧画给好几个地方：EGL 的正确打开方式

屏幕、视频编码器、离屏 pbuffer，在 EGL 眼里都是同一个上下文下的不同 `EGLSurface`。纹理和 FBO 属于上下文，所以在它们之间天然共享。录像时每帧的流程就是：

```
makeCurrent(编码器 surface) → 画一遍（带旋转）→ 打时间戳 → swap
makeCurrent(屏幕 surface)   → 画一遍（带圆角和监看）     → swap
```

两个容易漏的点：

- 创建 EGL 配置时要带 `EGL_RECORDABLE_ANDROID`，否则编码器的 Surface 可能不认你。
- **时间戳用相机传感器的时间**（`SurfaceTexture.getTimestamp()`），通过 `eglPresentationTimeANDROID` 交给编码器。音频那边用 `AudioRecord.getTimestamp()`，并且按相机的时间戳来源选同一个时钟（`REALTIME` 对 `BOOTTIME`，否则 `MONOTONIC`）。两边都减去第一帧视频的时间，音画就对齐了。我在模拟器上专门量过：第一个音频样本比第一帧视频晚 40ms 左右，起点是对齐的；结尾音频会比视频早收 0.1 秒上下，因为停止录像时先摘掉了麦克风回调、再让视频编码器把积压的帧吐完。

## 拍照：同一套管线，再跑一次

拍照最省事的做法是从预览里截一帧，但那只有 1080p。我选的是：Camera2 拍一张全幅 JPEG → 解码成位图 → 上传成 2D 纹理 → **用一套独立的、全分辨率的帧缓冲把整条管线再跑一遍** → 按朝向画到输出 FBO → `glReadPixels` 读回。

shader 一行不改，只是 input pass 换成 `sampler2D` 版本（`input_2d.frag`）。这就是当初坚持「效果参数与分辨率无关」的回报：光晕半径、颗粒大小在 4000 万像素的照片里和预览一模一样。

## 相机那边的两个「Camera2 没给」

**半自动曝光**。Camera2 的曝光只有两档：全自动（AE）和全手动。想要「只锁 ISO、快门自动」？没有。我的做法是在 AE 还开着的时候，一直记下它的 `ISO × 曝光时间`（扣掉曝光补偿），切到半自动时保持这个乘积，手动的那个改了，另一个反算出来，录像时快门还要受帧时长限制。代价是锁定之后场景亮度变了它不会跟——想要真的跟，可以用 GPU 算画面平均亮度做个反馈，留作练习。

**白平衡**。设备支持 `MANUAL_POST_PROCESSING` 时，我沿用 AWB 最后一次算出的色彩矩阵，只按色温调 R/B 增益，在 ISP 里完成；不支持就锁住 AWB，在 input pass 的线性空间乘增益。色温到增益的换算用的是 mired 差值（`1e6 / K`），斜率取自「钨丝灯 3200K → 日光 5500K 大约 +131 mired、红增益 ×0.65、蓝增益 ×1.67」这个经验值。不精确，但单调、手感对，而且 5500K 时增益正好是 1——从自动切到手动的那一下，画面不会跳。

## 冷宫名单：想过但没做的

| 方案 | 为什么没做 |
|---|---|
| 直方图用 compute shader | 需要 ES 3.1 + SSBO 原子操作。波形图已经够用，而且散点法只要 3.0 |
| 四面体插值的 3D LUT | 比三线性更准，但要在 shader 里手写，学习价值很高——所以留给你当练习 |
| 全管线 RGBA16F | 色带会更少，但带宽翻倍；目前只在最需要的光晕金字塔用了 |
| 拍照走 YUV_420_888 | 能跳过 JPEG 压缩，还能顺便学 YUV → RGB。可惜「预览 + YUV 最大尺寸」只有 FULL 级别才保证能配起来，JPEG 是 LEGACY 都保证的 |
| CameraX | 省事，但手动参数、色调曲线都要绕 Camera2Interop，而这个项目恰恰想把 Camera2 摸清楚 |
| 动态照片（实况） | 要常驻编码器维护环形缓冲，再拼进 JPEG 的 XMP 容器——是个好项目，但它考的是编码，不是 GL |

## 练习题

从易到难，每道题都只需要改一两个文件：

1. **加一个锐化滤镜**：在 film pass 末尾做 unsharp mask（原图 + (原图 − 模糊) × 强度）。提示：模糊可以直接借柔光的金字塔。
2. **四面体插值**：在 `film.frag` 里手写 tetrahedral LUT 插值，和硬件三线性对比渐变区域的色带。
3. **把 `signal`/`graded` 换成 RGBA16F**，用一张强烈的影调看色带变化，再用 GPU 性能分析工具看带宽代价。
4. **直方图**：仿照波形图，用散点 + 加法混合往一张 256x1 的 `R16F` 纹理里累加，再画出来。
5. **GPU 测光**：把画面缩到 1x1（`glGenerateMipmap` 或多级降采样），用 PBO 异步读回平均亮度，让半自动曝光能跟着场景变。
6. **RGB 分量示波器（parade）**：波形图的三通道版本，左中右各画一个通道。

做完这些，你对「相机里的 GPU 在忙什么」大概就比大部分人清楚了。至少，比三个月前的我清楚。
